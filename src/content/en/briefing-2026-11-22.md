## Developer Workflow Tips

### Anthropic published the six building blocks for writing always-on agents (11/13)

**Until now, most agents worked session by session — one request, one response, done — but Anthropic's official guide now lays out how to build "always-on agents" that keep context across sessions and act on events without waiting for a user to supervise them.** The core agent loop itself stays the same; it's the surrounding structure that creates the always-on experience, the guide explains. The six building blocks are: an event inbox (user messages, webhooks, and scheduled jobs land in a durable queue, with exactly one worker per inbox to prevent duplicate runs), timers (schedule follow-up checks and recurring jobs), memory (four kinds — user instructions, notes, past messages, and task progress — persisted so they survive even after a worker disappears), context management (compact or start a fresh session once things get long, but save anything important to memory first), permissions (unattended runs act under the user's own permissions, so credentials are injected by an external proxy, and any call that needs approval holds the session open while it waits for an answer), and an outbox (too many notifications become noise, so start quiet). As backdrop, the guide cites a long-horizon coding benchmark where Opus 5.5 cut the cost per solved task by 78% versus Opus 5, noting that this kind of implementation has only now become cost-practical.

```text
Event (user message / webhook / scheduled job) → lands in a durable queue → one worker per inbox processes it
  → runs using memory (instructions, notes, past messages, progress)
  → any call needing approval holds the session open and waits for an answer
  → timers schedule follow-ups or hand results off to the outbox → waits for the next event
```

**If you're designing an automated agent that keeps context across sessions and acts on its own, this structure is worth borrowing directly: queue events durably with one worker per inbox to prevent duplication and overwrites, and isolate risk by having an external proxy inject credentials for unattended permissions.** [Anthropic's official guide](https://claude.com/ko/resources/articles/building-always-on-agents) · [GeekNews](https://news.hada.io/topic?id=37550)

### VS Code gets a new `/workflows` command showing running workflows at a glance (v2.1.330)

**Until now, running several workflows at once in VS Code made it hard to tell which agent was working on what — starting with this release, the `/workflows` command opens an agent map showing exactly what's running.**

```bash
# To see running workflows in VS Code at a glance
/workflows
```

**If tracking progress across multiple agents and workflows in VS Code felt like a hassle, as of v2.1.330 a single `/workflows` command pulls up the agent map so you can check in.** [Full release notes](https://github.com/anthropics/claude-code/releases)

### `/config` search got smarter, now surfacing settings that start with what you type (v2.1.330)

**Until now, finding a setting in `/config` meant practically knowing its exact name — starting with this release, settings that start with what you typed are ranked first, so typing "effort" brings up the Model setting and typing "dark" or "light" brings up the Theme setting right away.**

**If you've been scrolling through a long list to find a setting in `/config`, as of v2.1.330 it's worth just typing whatever keyword comes to mind instead — it'll surface faster.** [Full release notes](https://github.com/anthropics/claude-code/releases)

One example had Codex handle an entire documentation-site deployment end to end — approving the deploy, shipping it 20 minutes ahead of the scheduled time, and confirming it landed — but the piece also noted limitations: computer-use history is still macOS-only, and the cloud version runs on a Linux VM, so it can't build iOS apps. Worth watching given how closely it tracks Claude Code's Code Mode, agent teams, and background sessions. [GeekNews](https://news.hada.io/topic?id=37556)
- **Inkling-2-Mini's quantization results — shrinking an 18.89GB model to 5.38GB — sparked a debate (11/22)**: LookAtMyQuant measured how much output damage each model component causes and allocated compression within a size budget accordingly, compressing the text weights so the 5.38GB model scored 67.0% on GSM8K and 36.6% on HumanEval (versus 73.5% and 40.2% for the original BF16 model) — beating, by their account, a comparison model that was 41% smaller on both evaluations. Comments pushed back, though, noting that by a 13-language KL-divergence measure it actually did worse than the comparison model, and that the GSM8K/HumanEval gaps fall within noise, making the claimed results look overstated. [GeekNews](https://news.hada.io/topic?id=37595)

## Recommended Reads

- **Why Vint Cerf never patented TCP/IP (11/21)**: TCP/IP was built for U.S. military command-and-control and for connecting allied nations, and 83-year-old Vint Cerf explains that since no one could know 25 years out who the allies would even be, it was released openly, without patents or licensing restrictions. He left Google this year after more than two decades there and is now helping Tolero, an interplanetary internet software company, and notes that "interoperability" — getting different systems to work together, the theme running through his whole career — now shows up again in the problem of getting AI agents built by different companies to talk to each other. Comments split between pointing out that monetization and venture-capital pressure make this kind of open thinking much harder today, and pushing back that patent-unencumbered innovation is still happening, citing Signal Protocol, RISC-V, and WireGuard. Worth a read if you're thinking about interoperability between AI agents — it revisits the same problem a predecessor faced half a century ago. [GeekNews](https://news.hada.io/topic?id=37578)
- **Running 15 million web servers on one VM: smoltcp, DPDK, AF_XDP (11/19)**: an experiment spinning up 15 million minimal web servers, each listening on a different IP, on a VM with 10GB of RAM and a single CPU core. Every guest ran inside a single-process runtime switched by a userspace scheduler, and the Rust-based TCP/IP stack smoltcp cut per-idle-server memory down to 620 bytes, far outrunning the kernel network stack (which ran out at around 2.5 million servers). The author admits the first calculation was wrong because they'd taken an LLM's claim that "idle connections cost zero memory" at face value, without checking it — missing the real kernel cost of roughly 3,300 bytes per socket. It's both a case for how much performance stripping away abstraction can unlock, and a concrete, numbers-backed example of where accepting an AI's assumptions unchecked goes wrong. [GeekNews](https://news.hada.io/topic?id=37470)
- **Deleting binder.c: replacing Android Binder's C implementation with Rust (11/22)**: Android's core inter-process communication driver, Binder, had its C implementation removed in Linux 7.4 and fully replaced with a Rust implementation after more than five years of work. Google's security team had flagged Binder as the OS component with the most CVEs relative to its code size, and new features have since been added only to the Rust version. The real problem turned out to be tail latency, not throughput: Rust's different locking approach occasionally caused rare ~20ms priority-inversion delays, which the team fixed by moving work outside the lock and switching a mutex to a spinlock; keeping compatibility with clients and vendor hooks that relied on internal tracepoints and reference counts was reportedly the hardest part. Comments argued over whether "most CVEs relative to code size" alone justifies a Rust rewrite, countered by the point that most actual Binder CVEs were use-after-free bugs — exactly the class of bug the Rust move was meant to address. If you're planning a large AI-assisted refactor, this is a useful look at where a five-year, security-motivated language migration actually gets stuck. [GeekNews](https://news.hada.io/topic?id=37594)

## Interesting Projects & Tools

- **codemap-search — a single-binary code-exploration MCP server for coding agents (11/21)**: born from the observation that when Claude Code or Codex is limited to read, find, and grep for exploring a local repo, it ends up making more calls, hitting output limits, or missing intermediate paths. Instead of costly indexing approaches like LSP or graph databases, it bundles Tree-sitter parsing, Tantivy BM25 search, call-relationship tracking, and read/find/grep into one tool, with configurable options for including test and generated files. On Grafana (about 24,000 files), indexing took 13-16 seconds and used 137MB of disk, and in a benchmark against an rg baseline and four other open-source MCP servers, it scored highest everywhere at 96-98 out of 108 points on accuracy — though every MCP tool used more tokens than rg, and the test scope was limited to one repo, one model, and three questions. [GitHub](https://github.com/buYoung/mcp/tree/main/apps/codemap-search) · [GeekNews](https://news.hada.io/topic?id=37568)
- **AS Screener — a local tool that filters hidden malicious instructions out of Claude Code and Codex skills (11/21)**: built around the concern that a SKILL.md file can hide instructions like "don't tell the user" or code that quietly exfiltrates SSH keys. Rather than installing the original text as-is, a separate, tool-less Claude instance rewrites just the skill's intent before installing it, and discards executables, hooks, and `.mcp.json` entirely. The author tested NVIDIA SkillSpector (v2.12.0) against malicious instructions written in Korean, Chinese, Japanese, and Spanish and found it scored everything 0 (safe) — missing all of them — which is why hidden-pattern rules for Korean, Chinese, Japanese, and English were added. Rewritten results only get installed after passing six automated checks plus human approval, and against a public set of 16,308 skill files it logged zero false positives and 7 warnings; it's still only been tested on Windows, though, and static rules catch only about 1 in 4 unfamiliar attack phrasings, so the author recommends also turning on LLM deep-scan. [GitHub](https://github.com/innoaz-dev/as-screener) · [GeekNews](https://news.hada.io/topic?id=37565)
