## 主要な新機能と実践活用

### Claude Ship — PRのレビュー・修正・承認までを任せられるベータ機能が公開されました（11/23）

**これまでClaude Codeでコードを書いた後、PRを出してレビューを受け、CIの失敗やマージコンフリクトに対応する作業は依然として人が手を動かす必要がありましたが、Anthropicが公式ブログでこの流れ全体を任せられるベータ機能Claude Shipを公開しました。** Code Review（正式リリース）はPRを複数の観点からレビューし、見つけた内容を検証・分類してPRに記録します。リポジトリごとにQuick・Standard・Deepのレビュー強度を選べます。PR Steward（ベータ）はCIの失敗・マージコンフリクト・レビューフィードバックに対応してPRを通過可能な状態に保ちつつ、プッシュごとに何を変更し、どう元に戻せるかをコメントで残しますが、自分で承認・マージすることはありません。Claude Approvals（ベータ）はリポジトリにファイルとして定義した承認ポリシーに従って軽微な変更を自動承認し、特定のケースでは人間の署名を要求します。Anthropicはまず観察専用モードで始めてからブランチ保護ルールに適用することを推奨しています。Team・Enterpriseプランでは GitHub リポジトリに使えますが、Zero Data Retention・HIPAA設定・顧客管理の暗号鍵を使う組織にはまだ提供されていません。

```bash
# 開発者が変更を作成した後
/ship
# → Claudeが変更をプッシュしてPRを開いた後、自ら見直し
#   フィードバックと失敗したチェックに対応します（マージするかどうかは権限・ブランチルールに従う）
```

**PRを出した後もCIの失敗やレビューフィードバックへの対応で文脈切り替えが多かったなら、Team・EnterpriseプランでGitHubリポジトリを使っている場合は`/ship`一つでレビューから修正までを任せ、自動承認の範囲はまず観察専用モードで検証してみる価値があります。** [Anthropic公式ブログ](https://claude.com/resources/articles/introducing-claude-ship)

### MCPサーバーがskill配布・バックグラウンド処理・中間確認依頼・ファイルアップロードまで対応するよう拡張されました（11/24）

**これまでMCPサーバーは主にClaudeが呼び出すツール（tool）を提供するだけでしたが、Anthropicが公式ブログでサーバーがClaudeを「もう一つのエージェントのように」扱えるようにする4つの機能を公開しました。** Skills over MCP（パブリックベータ）は、サーバーが複数ステップの作業ガイドや組織独自のプレイブックをskillとして一緒に配布できるようにし、Claudeは必要なときだけそれを読み込み、サーバーの更新に応じて自動的に最新化されます。Tasks（正式リリース）は時間のかかる作業やエージェントループ全体をサーバーがバックグラウンドで実行している間、Claudeが他の作業を続けられるようにします。Elicitation（正式リリース）は、サーバーが呼び出しの途中で一旦停止し、フォームやリンクでユーザーの確認（コスト承認、危険な操作の承認など）を得てから続行できるようにします。ファイルアップロード（近日公開）はPDF・スプレッドシート・画像をコンテキストウィンドウを経由せずサーバーへ直接送信します。Skills over MCPはPro・Max・Ultraではデフォルトで有効、Teamは管理者が有効化する必要があり、Enterpriseは近日対応予定です。

**MCPサーバーを自分で運用している、あるいはClaude Codeに複数のMCPサーバーを接続して使っているなら、サーバー側にskillを一緒に配布して追加インストールなしでガイドを伝えたり、コスト承認のような危険な操作の前にElicitationで確認ステップを挟む設計を検討してみる価値があります。** [Anthropic公式ブログ](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more)

## 開発者ワークフローティップス

### Claude Codeを組織全体に安全に広げる方法を整理したエンタープライズガイドが公開されました（11/23）

**これまでセキュリティ・技術リーダーがClaude Codeを組織規模に拡張する際、どの統制をどこに置くべきかは各自で整理する必要がありましたが、Anthropicは公式ガイドでリスクをゼロにするのではなく「可視化され、限界が明確な」状態にする3層の統制構造を提示しました。** 判断レイヤー（アラインメント学習、プロンプトインジェクション検知、意図と行動を照合するautoモード分類器、取り消しにくい操作に対する人間の承認）、固定境界レイヤー（優先度付きdenyルール、Bashコマンドをトークン単位で分解して検査する分析、コミットに含まれる機密情報をブロックするPreToolUseフック、OSレベルで隔離するローカルサンドボックス、作業ごとに新しく立ち上がるディスポーザブルVMであるクラウドセッション）、ポリシーレイヤー（デフォルトを拡張可能なbaselineと中央で強制するlockedに分け、`allowManagedDomainsOnly`・`allowManagedMcpServersOnly`・`disableBypassPermissionsMode`といった設定でロックする方式）で構成されます。資格情報の漏洩、検証されていないMCPサーバー・プラグイン・skill・`CLAUDE.md`、データ漏洩、プロンプトインジェクションを主要なリスクとして挙げ、感度の低いリポジトリで2週間のパイロットを実施し、分類器によるブロック・サンドボックスによるブロック・拒否されたネットワークアクセスを確認するよう推奨しています。

```text
判断レイヤー（アラインメント学習・インジェクション検知・autoモード分類器・人間の承認）
  → 固定境界レイヤー（権限ルール・Bash解析・フック・ローカルサンドボックス・クラウドセッション）
  → ポリシーレイヤー（baseline vs locked設定、中央強制）
  → 監査可能性（セッショントランスクリプト・OpenTelemetry・監査API）
```

**組織としてClaude Codeの導入範囲を広げる中で、どの統制を先にロックし、どれを開発者の裁量に任せるべきか悩んでいたなら、感度の低いリポジトリで2週間のパイロットを行い、分類器・サンドボックス・ネットワークブロックのログから確認していくこのガイドの出発点をそのまま参考にする価値があります。** [Anthropic公式ガイド](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents)

### 評価（eval）はAIエンジニアリングで最も過小評価されているスキルだという実践手法が公開されました（11/24）

**これまでモデルやプロンプトを変更した後に改善されたかどうかは単一の指標で判断しがちでしたが、この記事は指標を見る前にまず本番環境の失敗例を100件以上直接読んで分類することから始めるべきだと強調します。** プロンプトは捨てられ、モデルは数か月ごとに変わりますが、積み上げた失敗例のライブラリはその価値がずっと残るというのが核心的な主張です。スキーマ検証・正規表現・テスト用DBへのSQL実行のようにコードで確認できる項目はまず決定的チェックでふるい分け、コードで確認できない部分だけをLLM判定に任せるよう勧めます。RAGについては検索（recall@k、MRR、nDCG）と生成（根拠の忠実性）を別々に測定することで、どの段階が失敗しているかが明らかになると指摘します。エージェントについてはすべてのツール呼び出しをログに残し、精度・再現率・引数の正確さ・ステップ数を確認すべきだとし（3ステップで済む作業を14回呼び出した例を紹介）、毎回の実行が成功しなければならないpass^kでは、1回あたり80%の成功率でも5回連続で成功する確率は約33%にしかならないことを数値で示します。LLM判定を使う場合は100件以上を自分でラベル付けしてtrain・dev・testに分け、100件サンプルで80%の精度の95%信頼区間が±8ポイント程度になる点を挙げ、83%への変化はノイズに過ぎない可能性があると警告します。

**Claude Codeや自前のエージェントの性能改善を単一の指標だけで判断していたなら、失敗例から積み上げて決定的チェックとLLM判定を切り分け、pass@kではなくpass^kで信頼性を測り、小さなサンプルでの精度の差を信頼区間なしに改善と断定しないこの記事の方法論をそのまま適用してみる価値があります。** [GeekNews](https://news.hada.io/topic?id=37745)

**公式のstatus.claude.comを確認したところ、11/23の複数モデルでのエラーインシデント（11/24のブリーフィングで紹介済み）に続き、11/24 17:09~17:27 UTCの18分間にClaude Haiku 5.5でエラーが増加するインシデントが発生し、修正デプロイ後17:50 UTCに解決処理されました。** 同日（11/24）00:10 UTCからは、個人のMicrosoftアカウントでログインした一部ユーザーに対し、MacのExcel・Word・PowerPointでClaude for Microsoft 365アドインが表示されない問題が報告され、会社・学校アカウントには影響がないと案内されていますが、本日（11/25）時点でも調査中のままで、該当ユーザーはしばらくoffice.comのWeb版を使うことが推奨されています。本日（11/25）新たに報告されたインシデントはありませんが、claude.aiコンポーネントは現在リアルタイムステータスでDegraded Performance（性能低下）と表示されており、ページには特に説明が付いていません。Claude Codeを含む他のすべてのコンポーネントはOperational（正常）です。

**昨日（11/24）の朝にClaude Haiku 5.5でエラーを経験していたなら18分で解決した一時的な現象でしたが、Macで個人アカウントのClaude for Microsoft 365アドインを使っていたならまだ調査中の問題なので、当面office.comのWeb版を代替として使っておくのが安全であり、claude.aiのDegraded Performance表示も併せて注視する価値があります。** [Claude Status](https://status.claude.com)

### Zero Data Retentionを適用したEnterprise Frontier Safeguardsがパブリックベータに移行しました（11/23）

**これまでエンタープライズ顧客が安全対策とデータ非保持（Zero Data Retention）を同時に受けるにはプライベートベータへの申請が必要でしたが、Anthropicは公式ブログでヘルスケア・金融・法律分野を含む100社以上のプライベートベータ顧客を経て、パブリックベータに移行したと発表しました。** これまでのZDRがリクエスト単位でのみリスクを防いでいたのに対し、Enterprise Frontier Safeguards（EFS）は複数のリクエストに分割された悪用パターンまで検知しつつ、顧客自身が管理するクラウドストレージ（Amazon S3またはGoogle Cloud Storage）にモニタリングデータを保存することで、Anthropicもクラウドプロバイダーもデータを保持しないと説明しています。Claude Platform、AWS上のClaude Platform、Amazon Bedrock、Google Cloudで利用でき、Microsoft Foundry対応は「近日提供」とされています。リスクが検知されると顧客のクラウドストレージやAPIから読み取れるSafety Caseが生成されますが、ここには実際の入出力内容は含まれず、Anthropic側の人間が直接確認するレビュー手続きもないと強調されています。

**ヘルスケア・金融・法律のように機密性の高いデータを扱う中で、安全対策のためにデータ非保持のメリットを諦めざるを得なかったなら、パブリックベータに移行したEFSは顧客管理のストレージ費用を払う代わりに両方を同時に得られる選択肢になった点を検討する価値がありますが、Microsoft Foundry環境ではまだ対応前である点は留意が必要です。** [Anthropic公式ブログ](https://claude.com/resources/articles/zero-data-retention-with-enterprise-frontier-safeguards)

## 注目プロジェクト＆ツール

- **orca-orchestration-kit — Claude Codeのセッションを数十並列で一人が運用できる3層オーケストレーションキット（11/24）**: メインセッション（ユーザーとやり取りし意思決定を行う）・タスクマネージャー（作業の割り振りとマージを担当し、自分では実装しない）・ワーカーセッション（要件ごとにセッション・ブランチ・ワークツリーを一つ持つ）に役割を分け、共有基盤作業（W0）から並列要件（W1）・モジュール統合（W2）・システム統合（W3）までウェーブ単位で進めます。`req/*` → `int/<module>` → `int/common` → `main`の順でマージし、リベースや強制プッシュは使わず、作業の難易度に応じてClaude・Codex・Antigravity・Grokの中から契約済みのCLIとモデル・effortを自動で割り当てるルーティングも備えています。作者はセッション数そのものではなく重い作業自体が本当のボトルネックであること、隔離は最初から設計すべきであることを教訓として挙げています。`/plugin install orca-orchestration-kit --marketplace newrise0410/orca-orchestration-kit`でインストールでき、まだv0.5.0段階で慣習が変わり続けており、ドキュメントは韓国語中心です。[GitHub](https://github.com/newrise0410/orca-orchestration-kit) · [GeekNews](https://news.hada.io/topic?id=37768)
- **VerifyLens — AIが書いたコードを要件と照合し、確認済み・不一致・未確認として示すオープンソース（11/24）**: 「要件はすべて反映しました」というAIの言葉を信用できず、コードを一つひとつ照合する手間から生まれたツールで、要件ごとに根拠となったコードの行と実際に実行したJUnitテストを結び付けて表示します。「連続5回失敗したらアカウントをロックする」という要件に対し、AIが書いたコードが6回目でロックするようになっていれば、テストが通っているかどうかに関係なく「不一致」と判定する、という具合です。LLMを使わずTypeScriptコンパイラ・gitの変更履歴・テスト結果だけで判断するため、同じ入力には常に同じ結果を返し、根拠が不確かな場合は「問題なし」ではなく「未確認」として残します。ただしバージョン0.26では「確認済み」判定の半数が的外れな行を根拠にしていたほどまだ誤判定があり、対応言語はTypeScript・JavaScriptのみで、実際のClaude Codeエージェントセッションではまだ検証されていないと作者自身が明らかにしています。インストール不要で、体験ページに要件・コードや公開GitHub PRのURLを直接入力して試せます。[GitHub](https://github.com/DamunKorea/verifylens) · [GeekNews](https://news.hada.io/topic?id=37720)
