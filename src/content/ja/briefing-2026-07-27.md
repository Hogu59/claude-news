## 主要な新機能と実践活用

### `agent-memory-2026-07-22`ベータ — Managed Agentsメモリ一覧APIのソート・ページネーション方式が変わる

Claude APIが**`agent-memory-2026-07-22`ベータヘッダー**を通じて、Managed Agentsのメモリ一覧エンドポイント(`GET /v1/memory_stores/{memory_store_id}/memories`)の挙動を変更しました。既存の`managed-agents-2026-04-01`を置き換えるヘッダーです。

- **何が変わるか**: 結果は今後**サーバー側が定める安定した順序**でのみ返されるようになり、`order_by`・`order`パラメータは無視されます。`depth`は**0・1または省略のみ許可**され、それ以外の値は400エラーになります。`path_prefix`は必ず`/`で終わる必要があり、部分文字列ではなく**パスセグメント全体の完全一致**でマッチします。
- **注意すべきbreaking change**: このヘッダーなしで発行された**ページカーソルは新ヘッダーと併用できず**、導入時点で最初のページからやり直す必要があります。同じメモリストアのエンドポイント呼び出しで**`managed-agents-2026-04-01`とこのヘッダーを同時に送ると400エラー**になります。
- **SDKはすでに対応済み**: Python(0.116.0)・TypeScript(0.110.0)・Go(1.56.0)・Java(2.48.0)・Ruby(1.55.0)・PHP(0.36.0)・C#(12.35.0)・CLI(1.16.0)の各SDKは、メモリストア呼び出しでこのヘッダーをデフォルトで送るようすでに更新されています。

```python
response = client.beta.memory_stores.memories.list(
    memory_store_id="...",
    path_prefix="projects/acme/",   # 今後はセグメント完全一致、末尾の / 必須
    depth=1,                        # 0、1、または省略のみ許可
    extra_headers={"anthropic-beta": "agent-memory-2026-07-22"},
)
```

ポイントは**「長時間稼働するエージェントのメモリをページ単位で巡回するコードが、今回の更新で静かに壊れる可能性がある」**という点です — SDKを最新版に上げたチームはすでに新ヘッダーを自動で送っている可能性が高いので、Managed Agentsのメモリを独自のページネーションロジックで扱っている場合は、今日のうちに`path_prefix`・`depth`・カーソル再発行の要否を確認してください。[Claude Platform Docs](https://platform.claude.com/docs/en/managed-agents/memory) · [Claude Platform release notes](https://platform.claude.com/docs/en/release-notes/api)

## 開発者ワークフローティップス

### マイクロカーネルを見直す時期 — エージェントの分離境界を設計する際に参考になる知見

かつてはオーバーヘッドのせいで実用性に欠けた**マイクロカーネルアーキテクチャ**が、今日では一般的になった**IOMMUと共有メモリ**のおかげで再び現実的な選択肢になり得るという再評価記事です。

- **核心の論点**: ドライバ・サブシステムをカーネルではなく**ユーザー空間に分離**すれば、不具合や攻撃が及ぼす影響範囲を狭め、**セキュリティ・信頼性・モジュール性**を同時に高められます — 以前はこの分離にかかるコンテキストスイッチのコストが大きすぎましたが、IOMMUがそのコストの大部分をハードウェアレベルで吸収してくれます。
- **なぜ今注目すべきか**: 今週のClaude Codeのリリースで磨きがかけられ続けている`sandbox.filesystem.disabled`(v2.1.216)・`sandbox.network.strictAllowlist`(v2.1.219)のような細粒度の分離オプションも、同じ方向の判断です — **分離境界をひとつの大きな壁にするのではなく、必要な分だけ細かく区切るほうが現実的に扱えるようになった**という流れです。

エージェントが実行するツール・コマンドのために独自のサンドボックスや実行分離レイヤーを設計しているチームなら、「全部許可か全部遮断か」ではなく**狭い単位で分離境界を区切る設計**がなぜ再び実用的な選択肢になったのか、確認する価値があります。[GeekNews](https://news.hada.io/topic?id=31836)

### 8ドルのマイクロコントローラでLLMを動かす方法 — Per-Layer EmbeddingsでフラッシュメモリをRAMのように使う

**ESP32-S3**(約8ドル)でサーバー接続なしに**2,890万パラメータの言語モデル**を動かし、毎秒約9トークンでテキストを出力した実測事例です。

- **核心の手法**: 全パラメータのうち**2,500万個を低速なフラッシュメモリに置いたまま**、トークンを生成するたびに必要な**約6行・450バイトだけをフラッシュから読み込むPer-Layer Embeddings(PLE)**方式を使います — RAMに載せきれないモデルを、そのつど必要な断片だけストリーミングして動かす構造です。
- **どこに応用できるか**: クラウド接続なしにオフラインで動作する必要がある小型エージェントや組み込みコパイロットを作るなら、**「モデル全体をメモリに載せられないなら、レイヤー単位で必要な断片だけを低速ストレージからストリーミングする」**というこのパターンがそのまま参考になります。

エージェントをクラウドAPI呼び出しではなくローカル・エッジデバイスに直接組み込む実験をしている開発者にとっては、メモリ制約を回避する具体的な設計パターンとして注目に値します。[GeekNews](https://news.hada.io/topic?id=31832)

## 注目プロジェクト＆ツール

- **Show GN: telepty — 複数マシンに散らばったAIエージェントセッションのコントロールプレーン**: teleptyは、**claude・codex・geminiのようなターミナルAI CLIセッション**が複数マシンに散らばっている場合に、リモートで指示を送り画面を読み取れるようにする軽量ツールです。核心の設計は、**推論とタスク実行は各エージェントがそのまま行い**(データプレーン)、teleptyはそれらのセッションをアドレスで呼び出して指示を伝達するだけの**コントロールプレーン**役に徹する点です。7/25のブリーフィングが扱ったADHDev(Web/モバイル制御に並行タスクの自動マージまで含む)がより重量級のオールインワン型アプローチだったとすれば、teleptyは**セッションを呼び出して伝達するだけの薄いレイヤー**に特化した対照的な選択です — 複数マシンでClaude Codeセッションを同時に動かしている人なら、軽量なリモート制御だけを解決したいときに参考になります。[GeekNews](https://news.hada.io/topic?id=31842)
